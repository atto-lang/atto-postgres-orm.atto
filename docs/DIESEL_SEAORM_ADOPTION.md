# Diesel + SeaORM lessons for native Oreslang PostgreSQL ORM

**Status: proposed design and acceptance criteria, not an implemented API or executed compiler/DB result.** As of this draft, `src/pg.ores` is a synchronous planner and does not issue queries, provide a PostgreSQL connection or establish tenant authority. This document does **not** claim to implement a Diesel/SeaORM equivalent.

## Evidence-backed ideas to adopt

### Diesel: make the default path statically provable

Diesel uses declared schema, typed expressions, typed SQL-to-model mapping and trait bounds to reject invalid query combinations at compile time. Its schema can be generated by database introspection, and its `Queryable`/`Selectable` and `AsChangeset` features constrain projection and write shapes.

Oreslang translation:

1. Build or import a **versioned, signed/verified schema manifest** at AOT generation time. Generate nominal `Table<T>`, `Column<T, PgType, Nullability>`, `Projection<T>`, `Relation<From,To>` and `ModelCodec<T>` descriptors using hygienic compile-time macros/typeclasses, not reflection.
2. SQL operations are named methods (`eq`, `and`, `join`, `order_by`, `select`) with explicit typeclass constraints; **no operator overloading**, implicit conversions or dynamic SQL fragments.
3. Separate the compile-time typed AST from an explicitly bounded, validated dynamic query facility. The default path rejects unknown table/column references, incompatible joins, nonboolean filters, unordered pagination, invalid aggregates, unsafe casts and incompatible projection/decoder shape before execution. Dynamic queries still validate every node and never interpolate raw SQL.
4. Encode compile-fail tests: a `Text` column cannot be equated to a `Uuid` value, a selected nullable `Uuid?` cannot decode to nonnullable `Uuid`, a column from table B cannot appear in table A without a valid join, and a model projection must match count, order **and** types. Errors should identify offending schema/field instead of reporting only a generic typeclass mismatch.
5. Generate separate `Insert<T>`, `Patch<T>` and `Row<T>` codec shapes. Composite keys, `RETURNING`, FK relations and SQL type/OID mapping must be statically known wherever the schema is known. No implicit `SELECT *` in generated repositories.
6. Maintain migration versions and reversible steps when possible, but require review for destructive or nontransactional DDL. Do not equate a migration declaration with a successfully applied migration.

### SeaORM 2.0: async operations and explicit change tracking

SeaORM 2.0 distinguishes `ActiveValue::Set(v)`, `Unchanged(v)` and `NotSet`; it supports entity-first/schema-first workflows, async transactions, relation loaders and nested active models. It uses join/batch strategies to reduce N+1 loading.

Oreslang translation:

1. Define a **closed** AOT `Change<T>` algebra: `NotSet | Unchanged(T) | Set(Option<T>)` for **nullable** fields; for nonnullable fields, `Set(T)` only. This is a *proposed algebra*, not current Oreslang syntax. No Java `null`, and never conflate `NotSet` (omit) with `Set(None)` (write SQL NULL).
2. For INSERT: omit `NotSet` fields only when a verified database default/generated column exists; require all other mandatory fields. `Unchanged` is invalid for new models unless explicitly resolved to `Set`. SQL NULL must be rejected for nonnullable columns before binding.
3. For UPDATE: `NotSet` and `Unchanged` emit **no assignment**; `Set(Some(v))` assigns a bound value; `Set(None)` assigns SQL NULL on nullable columns. No-change updates are a reported no-op, never a silent full-row overwrite. Enforce immutable PK/tenant fields except an explicit, separately authorized migration operation.
4. Distinguish **input DTO** validation from **row snapshot** and **write patch** validation. Zorde refinement checks execute at admission and after decode; Serde-like codecs encode the PostgreSQL wire values. No field conversion or hidden default silently mutates another field.
5. Entity relations are explicit descriptors with join cardinality, composite keys and tenant predicates. Offer **opt-in** `load_with` / batched DataLoader policies with configurable max batch size and bounded memory, selecting single-query JOIN for 1:1 when safe and batched 1:N for cardinality expansion. Never trigger I/O merely by reading an object property.
6. Nested writes require a verified relation graph, deterministic order, bounded fan-out, single actor-owned transaction, tenant capability and explicit cascade authorization; cycle detection, rollback and compensation on cancellation are mandatory. No implicit cascading deletes.
7. Async streams, transactions and connection pooling must use actor-confined, generation-fenced leases, structured concurrency ownership, timeouts, backpressure and exactly-once terminal receipts. Neither `save` nor a transaction closure should accidentally block a carrier.

## Resolve Diesel (static) vs SeaORM (dynamic) explicitly

| Concern | Default public Oreslang API | Restricted dynamic API |
| --- | --- | --- |
| Tables/columns | compile-generated nominal schema descriptors | runtime lookup against an approved, versioned schema capability only |
| Query expressions | statically checked typeclass AST | checked AST with `Result<QueryPlan, QueryError>` and depth/size quotas |
| Projection/decoding | generated `Projection<T>` + `DecodePg<T>` | explicit heterogeneous row result, OID/nullability checks per field |
| Change tracking | generated, typed `Change<T>` per column | typed patch values with field allowlist and explicit optionality |
| Relations | generated FK/PK descriptors | validated relation registry, bounded join/batch planner |
| Execution | async actor-scoped capability | async actor-scoped capability; **no bypass** of tenant/role/RLS |
| Raw SQL | explicit privileged trusted-only API | **not** part of ordinary request-facing repositories |

A schema manifest must include catalog schema name, relation/column identity, type OID+modifier, nullability, keys, defaults, constraints and version/hash. At runtime, verify the manifest against the catalog or an authenticated migration receipt before admitting queries. A safe identifier `string` is **not** an authority-bearing table descriptor.

## SQL golden contracts (expected PostgreSQL SQL, *not* executed)

Assume a verified `docs(workspace_id uuid NOT NULL, id uuid PRIMARY KEY, title text NOT NULL, comment text NULL)` descriptor, and explicit transaction-scoped tenant authorization:

- **Projection + filter:** `SELECT "id", "title" FROM "docs" WHERE "workspace_id" = $1::uuid AND "id" = $2::uuid`; binds [Uuid(workspace), Uuid(id)]. No `SELECT *`, no string literal interpolation.
- **Only one changed field:** patch `title=Set("new")`, `comment=NotSet` => `UPDATE "docs" SET "title" = $1::text WHERE "workspace_id" = $2::uuid AND "id" = $3::uuid RETURNING "id", "title", "comment"`; nullable `comment` is untouched.
- **Explicit NULL:** patch `comment=Set(None)` => `UPDATE "docs" SET "comment" = $1::text WHERE "workspace_id" = $2::uuid AND "id" = $3::uuid`, with a typed NULL bind. The adapter must send PostgreSQL NULL, not the four-character text `null` and never replace it with `NotSet`.
- **No change:** patch `title=Unchanged("old")`, `comment=NotSet` => **no UPDATE statement**; return `NoChanges`, distinguishable from a successful affected-row count.
- **Explicit relation load:** for `docs` with many `comments`, use bounded parent SELECT + tenant-scoped `WHERE doc_id IN (...)` batch(es), or a constrained join where cardinality makes that preferable. Never issue an unbounded query per parent.

These are illustrative SQL templates. A planner must reject an invalid `Uuid` string at validation/admission before encoding its bind, and SQL text alone cannot prove authorization or safe execution.

## Atomicity and error design

- Error families: `SchemaMismatch`, `TypeMismatch`, `NullabilityViolation`, `InvalidChangeState`, `UnadmittedField`, `TenantDenied`, `StaleGeneration`, `TransactionClosed`, `ResourceLimit`, `Cancelled`, `DbError`. Include bounded field path and stable error code, but redact PII and SQL parameters.
- Database write receipts carry affected row count, query/transaction identity, generation and cancellation outcome. Retry only operations proven idempotent with explicit idempotency keys; never silently retry a partially committed transaction.
- `FOR UPDATE`, isolation level and transaction savepoints must be explicit and checked against the concrete PostgreSQL connection. In-flight queries pin a connection generation across suspension; rollback on cancellation/timeout is verified before returning it to the pool.
- Validate tenant through authenticated driver capability + real PostgreSQL role/RLS, not a client-settable `workspace_id` string alone.

## Implementation slices and review gates

1. **P0**: `PgType`, `DbValue` and `DecodePg<T>`/ `EncodePg<T>`; typed bind and OID checks; null/no-value distinction in pure planner; separate compile-time descriptors from mutable legacy plans.
2. **P0**: closed typed expressions + generated schema manifest + strict projection decoder. Compile-fail tests MUST exercise mismatched values, relations and projection shapes.
3. **P0**: authenticated async connection/transaction capability with RLS and generation fences, then actual PostgreSQL 17 tests. No execution through trusted legacy SQL strings without a distinct privilege.
4. **P1**: generated `Change<T>`/patch encoder with `NotSet`, `Unchanged` and `Set`, using no implicit conversions; nullability, PK/tenant update restrictions and empty-patch behavior.
5. **P1**: explicit relation loader, bounded JOIN/batch planner, nested-write transaction contracts, N+1/budget tests and deterministic pagination.
6. **P1**: deterministic schema-first introspection plus entity-first AOT generation, migration drift detection, up/down contracts, review/rollback.
7. **Release**: native compiler tests at exact SHA, emitted SQL golden receipts, independent live PostgreSQL and RLS adversarial tests, cancellation/pooling/streaming runs, and executable backend parity. **Zero-step CI is not test evidence.**

See `tests/DIESEL_SEAORM_ACCEPTANCE.md` for positive, negative, compile-fail, and concurrency/tenant test scenarios.
